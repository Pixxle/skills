### Opening a PR

Run this at the end of every playbook that ships a change.

1. **Worktree.** Work from a git worktree off trunk, on your feature branch. Subagents inherit it. Several subagents on the same branch each get their own worktree, or run `git fetch && git reset --hard origin/<branch>` between them. On a dirty branch with unrelated work, patch the work out, start a fresh worktree, and apply the patch there. In a snarled worktree, reset from trunk and redo the change minimally. Open the PR early when CI and bots should run alongside the work (Autopilot and Orchestrate owners do this). Real-surface proof ([`principle-prove-it-works`](../../principle-prove-it-works/SKILL.md)) and verifiable commit sequence ([`principle-sequence-verifiable-units`](../../principle-sequence-verifiable-units/SKILL.md)) must hold before you declare code-ready or ask for review. They do not block the create call.
2. **Commits.** Commit liberally. Rebase into small, ordered commits before you open a PR, or before code-ready when the PR opened early. Each commit is a future PR. It lands on its own, and its place in the order tells the story. Amend when the fix belongs in a commit you just made. Make a new commit when the fix is separable. A commit body does not restate the subject.
3. **Gates and writing.** Before each commit, slop-strip the diff. Remove comments a human would not write, defensive checks and try/catch blocks abnormal for that area of the code, casts that dodge the type checker, dead compatibility paths, unrelated edits, and style that breaks from the file. Before you ask for review, read and follow [`no-comments`](../../no-comments/SKILL.md) on the scoped diff. Write every PR title, description, commit subject, and commit body in plain technical English, then read and follow [`unslop`](../../unslop/SKILL.md) on that prose.
   - Cut every word that does no work. "In order to" is "to". Use the short, everyday word: "use", not "utilize".
   - Talk to the reader in the present tense and say who does what. Put a condition before the instruction or step it guards. Never write "simply", "easy", or "quickly".
   - One thought per sentence. Split a sentence past about 25 words.
   - One word per action, kept everywhere. Call each thing by one name. Keep "the" and "a". Prefer a plain verb over an `-ing` form where one works.
   - Write the real symbol, file, flag, or command name, not a synonym for it. Make every "it" and "this" point at one obvious thing.
   - Keep "only" and "not" next to the word they change. Break up long noun strings. Give every clause its own verb.
   - No idioms, metaphors, Latin abbreviations, slashes for "or", or semicolons.
   - Make every count or tree claim true at the commit that lands it, and include the command that regenerates it.
   - When a rule makes a sentence worse, fix the sentence another way or leave it alone.
4. **Titles.** Conventional Commits, `type(scope): subject`, with no trailing period. The type is one such as `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. The scope is the area, such as `scripts` or a skill's name. The subject is short and imperative, and it names a real symbol when one carries the change, for example `fix(babysit): read watch-pr verdict before polling`. The PR title and every commit subject follow this form.
5. **PR body.** A one-minute briefing for a reviewer who has the diff, not a lab notebook. It says why the change exists, what it leaves out, what it could break, and how you proved it works. Write short, simple sentences with few identifiers and no walls of text. The body becomes the squash commit body, so keep it under about 40 lines. Use `##` headings, not bold lead-ins, in this order, and drop a section with nothing to say.
   - `## Why` opens with the user's goal as you restated it at session start, then the problem and approach, in 1 to 3 short sentences. No SHAs, rebase genealogy, or "based on main" preamble.
   - `## What changed` is 1 to 3 short bullets. Name a real symbol or path only when it carries the change. Name both sides of a rename or retarget.
   - `## Scope` is always present. Give 1 to 3 short items on what the PR covers and what it deliberately leaves out (a follow-up, a known gap). No symbols, paths, or file-by-file essay.
   - `## Tradeoffs` lists only rejected alternatives a reviewer would otherwise ask about. Skip it when there was no real choice.
   - `## Blast Radius` is 1 or 2 sentences on who or what the change touches and why that is safe or risky. If main is red, state the cost of leaving it red.
   - `## Verification` is 1 to 3 bullets, each a real run path and its outcome. For perf, give one primary number with its unit as `before → after`, and link the arena or benchmark directory for the rest. No sample-size methodology, lane recitals, or metric tables.

   After the sections, attach videos or screenshots when they prove a claim. Full SHAs, lane recitals from parallel runs, lever-correction essays, file-by-file checklists, and "CLEAN" verdicts go in a linked artifact, not the body.
6. **Forge.** Resolve the forge before the first PR operation, and keep that choice for create, edit, view, watch, and merge. The GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin resolves the repository, prefer `origin pr ...` for every PR operation. If Origin is absent or cannot resolve the repository, stay on `gh` and record the fallback. Do not require Graphite (`gt`). When the run provides a built-in PR tool, create, edit, retarget, and mark ready through it, never through a forge CLI. A CLI-made PR misses what the tool tracks. Use the resolved forge for everything the tool does not cover, and for every PR operation when the run has no such tool.
7. **Size and stacks.** Prefer five narrow PRs to one large PR. A stack is a base-branch chain. The root PR targets trunk. Each child branch rebases onto its parent's exact tip, and its PR targets the parent branch. As a parent merges, move its child onto trunk per step 4 of [`shipping`](../../shipping/SKILL.md). Without a built-in PR tool, create a child with `gh pr create --base <parent-branch>` and retarget one with `gh pr edit <pr> --base <parent-branch>`, or the resolved forge's equivalents (`origin pr create --status open --base <parent-branch>`, `origin pr edit <pr> --base <parent-branch>`). Branch from trunk only for independent work. Rebase on trunk before substantial stack work.
8. **Readiness.** Open every PR ready for review, not as a draft, unless the user asked for a draft. A built-in PR tool can default to draft, so turn its draft option off on every creation call. With `gh`, omit `--draft`. With Origin, pass `--status open`. If a PR still opens as a draft, mark it ready through the PR tool, or run `gh pr ready <number>` or `origin pr ready <number>` per the resolved forge. Run `gh pr view <number>` or `origin pr view <number>` before you refer to a PR's status.
9. **Not babysit.** Opening a PR does not start a babysit. Post the URL and keep building. Finish the phase or the stack first. Run a separate [Babysit](babysit.md) pass only when the user asks for one after the whole stack exists. A babysit for each new PR stalls the build and spends checks on commits that later waves restart. Push back when feedback drifts from the user's intent.

A subagent that opens a PR runs the slop-strip and [`no-comments`](../../no-comments/SKILL.md) gates from step 3 and posts the URL. It returns to the parent without babysitting, unless it is an owner in [Autopilot full](autopilot-full.md), [Autopilot stack](autopilot-stack.md), or [Orchestrate](orchestrate.md). That owner's brief or kickoff assigns the babysit loop and is the ask [Babysit](babysit.md) waits for. An Autopilot owner starts the loop after its code-ready report. Every such owner reports merge-ready and is exempt from the rules here and in Babysit that hold babysitting until a whole stack is built.

**Reply:** PR URL, stack base if any, verification summary.
