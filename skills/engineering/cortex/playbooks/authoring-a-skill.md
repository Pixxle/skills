### Authoring a skill

**You own the skill's voice and structure for this collection.** Use this for writing a new skill or modifying an existing one. Approved [`reflect`](../../../productivity/reflect/SKILL.md) edits and broken-skill fixes found mid-task come through here too, each in its own change.

1. Read and follow [`write-a-skill`](../../../productivity/write-a-skill/SKILL.md).
2. Follow the maintenance rules in the repo's `AGENTS.md` or `CLAUDE.md`. The folder name matches the frontmatter `name`. Frontmatter keys stay within what those rules allow. Every skill is explicit-only, so a new skill ships that way. Its frontmatter sets `disable-model-invocation: true`, and its folder ships `agents/openai.yaml` setting `policy.allow_implicit_invocation: false`. The user starts it by name, and a router or sibling loads it by a link to its `SKILL.md`. So write every backticked skill name as that link, and phrase routing as "read and follow", never "invoke". Use capability terms, never runtime tool names or model slugs. Use relative resource paths. Register the skill in `.claude-plugin/plugin.json` and the bucket README. List a pstack-derived skill or agent in `NOTICE.md`.
3. **Write less.** When in doubt, delete. Keep only prose that changes a decision. Tell the agent to do the thing and skip the reason. Explain only when the rule is confusing without one. Match tone to scope. Point at structural sources (types, READMEs, config) per [`principle-encode-lessons-in-structure`](../../principle-encode-lessons-in-structure/SKILL.md). Delegate to siblings by path. Don't restate them. To encode a rule a lint, script, or check could enforce, read and follow [`correct`](../../correct/SKILL.md) instead of adding prose. When you keep hitting a workflow that no skill captures, propose a new skill.
4. **Validate.** Run `scripts/check-skills.sh` when the repo has it, and fix every finding. Otherwise check by hand that the frontmatter has `name` and `description`, every referenced file exists, and every cross-skill link resolves. After you add, rename, move, or remove a skill or agent, re-run `scripts/link-skills.sh`, then `scripts/check-skills.sh --installed`.
5. **Test cases if structural.** A change to a script, a check, or another deterministic step gets test cases, such as a fixture in `scripts/test-check-skills.sh` for a new checker rule. Skip them for a subjective change.
6. For an edit that changes agent behavior, run the [Eval](eval.md) playbook before trusting it. A fix written from one session tends to overfit that session.
7. Run [Opening a PR](opening-a-pr.md). A caller that needs its own go-ahead before the PR, such as [`reflect`](../../../productivity/reflect/SKILL.md), stops before this step and reports.

**Reply:** skill path, summary of the skill, key design choices, validation output, eval verdict or `skip: <reason>`, registration and link notes.
