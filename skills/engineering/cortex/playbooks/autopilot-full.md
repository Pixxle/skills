### Autopilot full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge. Nothing merges until your verifiers, none of which wrote the code, have proven the code that lands.**

You are the root of the program. Owners report to you, and you report to the operator. A verdict covers one patch, and green CI covers one head. Step 4 runs a full verification fan-out once, and again only for a major change. The patch-id rule in [`shipping`](../../shipping/SKILL.md) can carry a lane's result to a new head. Every new head still needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items. Items the operator names as theirs, and PRs outside the queue, stop at merge-ready. A request to state the plan is not a go. The operator's go is the ask to ship the queue's own PRs and nothing beyond them. The rest of the Always-pause list in [`principles`](../../principles/SKILL.md#autonomy) still binds.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program and hand the choice to every owner. GitHub CLI (`gh`) is the default. Use another forge CLI, such as Origin's, only when it is installed and resolves the repository. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`).

   Each owner agent is a fresh background subagent of the general kind. It is not a [`cortex-agent`](../../../../agents/cortex-agent.md) delegate, because a delegate never follows another workflow and stops when its task needs one. Pick its model by its PR's difficulty, per [Subagents](../references/subagents.md). It works in its own worktree and branch, per [`principle-separate-before-serializing-shared-state`](../../principle-separate-before-serializing-shared-state/SKILL.md). Its brief gives absolute paths. The owner reads [cortex's `SKILL.md`](../SKILL.md) and [`principles`](../../principles/SKILL.md) in full first, as rules for its own work, not as a playbook to run. It builds, opens its PR under the gates in [Opening a PR](opening-a-pr.md), and proves the change on the real artifact. It reads and follows [`babysit`](../../babysit/SKILL.md) to get to green. It reads and follows [`shipping`](../../shipping/SKILL.md) to merge once steps 4 and 5 clear it. This playbook stays in your chat.

   An owner is a role, and the role outlives its agent. Each owner agent returns at a report point: the code-ready head, each later head, merge-ready, or the merge. You record the report. Then a fresh owner agent takes the role's next round. Its brief carries consolidated scope: the original brief, every later directive, the prior agent's report, the branch, and the worktree path. A round never runs an open-ended babysit loop. It babysits until its next report point, so its turn ends. Between report points, the owner agent writes its state to its trail file in the program store, so a replacement can resume mid-round.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip in step 3 of [Opening a PR](opening-a-pr.md), and after the owner reads and follows [`no-comments`](../../no-comments/SKILL.md) on the diff, so the full verification runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head. Report merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push, and before any later push that needs a verifier.

   The brief assigns the babysit loop, and that brief is the ask [`babysit`](../../babysit/SKILL.md) waits for. The owner starts babysitting after its code-ready report. It is exempt from the rules in Opening a PR and [`babysit`](../../babysit/SKILL.md) that hold babysitting until a whole stack is built. A babysit never mutates stack topology and reports rebases to the PR's owner. An owner babysitting its own PR is that owner, so it rebases its own branch and pushes per the force-push rule below.

   Assume any owner agent can die mid-run. Soon after starting, the owner pushes its branch and starts a decision trail: it reads and follows [`handoff`](../../handoff/SKILL.md) in decision-trail mode. The trail lives in the program store, one directory you create outside every worktree and name in every brief. Each owner writes its own trail file, so no two agents write the same file. Push each finished unit before you start the next. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that store, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over. On any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Verify once, with parallel verifiers.** A full verification fan-out runs once, at the code-ready head. Another runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. A wording-only change gets none. Spawn independent verifiers in parallel at the code-ready SHA, and name that SHA in each brief. None of them wrote the code. Each runs on a different model family than the author when the runtime offers one. They re-run the gates, prove the load-bearing behavior live on the real surface, and audit the diff.
   - The live lane drives the change through the repo's `verify-*` skill, or through a named driver when the repo has none.
   - The audit lane reads and follows [`swarm`](../../swarm/SKILL.md) on the PR's diff at the named SHA (review panel from [`perspectives`](../../swarm/references/perspectives.md)). When structural quality is in scope, spawn [`thermo-nuclear-code-quality-review`](../../thermo-nuclear-code-quality-review/SKILL.md) in parallel with that audit.
   - A contested or hard-to-reverse change, or a finding that reading cannot confirm, adds a lane that reads and follows [`interrogate`](../../interrogate/SKILL.md) at the named SHA. Only a finding a rerun proves survives there.

   [`swarm`](../../swarm/SKILL.md) and [`interrogate`](../../interrogate/SKILL.md) each spawn their own subagents. When the runtime does not let a subagent spawn subagents, read and follow that lane's skill yourself at the named SHA, in place of a lane agent. A lane never stands in for its skill with a one-agent read.

   Each lane records the SHA it ran and lists every problem it can prove, not only the first. Drop a result that does not name its SHA, and respawn that lane once. A second miss is a gap. A gap is not a pass. The verdict is not clean until every lane spawned at that head has a result. It is also not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked. Post the verdict on the PR as `PASS`, `PASS+NOTES`, or `FAIL`, the verdicts [`shipping`](../../shipping/SKILL.md) lands on.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, does not block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks. Everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. The owner reads and follows [`shipping`](../../shipping/SKILL.md) to land. Your step 4 verdict is its independent verdict. Its patch-id rule decides whether that verdict survives a rebase. The owner reads the PR back after the merge command, because a queued merge or an armed auto-merge is not a merge. Once the verifiers' lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends.
   - Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR.
   - A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head. That install tests the lockfile that would land. A failing install means the rebase must repair it.
   - When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass.
   - Otherwise merge.

   If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm a recurring hourly wake-up that audits until no delegated work is left, because long runs drift and agents stall silently. When the runtime cannot schedule one, start a background command that sleeps for the hour and then exits. Treat its exit as the tick, and start the next one at the end of each tick. An audit run only when an owner reports is no substitute, because a stalled owner never reports. If the runtime offers no timed wake-up of any kind, tell the operator at the go that a silent stall goes unseen until they check in. Each tick re-reads this playbook and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. Each tick probes every agent, down to the leaf lanes, and judges each by its side effects (pushes, PR activity, trail rows), because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime. So is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once with a fresh one that carries consolidated scope, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up. A tick that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Catching the operator up.** Keep the catch-up read-only. Check the live state of each PR, CI run, and agent before you report it, with `gh pr view` and `gh pr checks` or the resolved forge's equivalents, never an owner's last report. Check each number against its source, and say so when you correct one. Use plain words and short sentences. Open with what waits on the operator, or say nothing does. Say what changed for them since their last message, not how you did it. List every call only they can make, with your pick. For each call, give its link, what it changes for users, the evidence behind your pick, and its risk, even when the risk is low. Write "unknown" for a fact the call needs that you do not have. List every item. Never cut one, and never put a count or a link in place of the list. The operator must be able to decide each call from the reply alone.

**Reply:** catch the operator up. Cover each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
