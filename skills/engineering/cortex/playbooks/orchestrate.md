### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. For one ambitious run that needs a bespoke workflow, read and follow [`figure-it-out`](../../figure-it-out/SKILL.md). A standing program comes here instead, even a migration across many call sites, because that skill designs one run and this playbook runs the program. One task driven to a predicate is [Autonomous run](autonomous-run.md). So is work that one agent could finish inside the session's budget, however program-shaped the phrasing sounds. That work is not a program.

Run it with the runtime's own capabilities. Spawn workers as background subagents. Keep the program's state in the program store, one directory outside every worktree that you create at the start and name in every kickoff. When a [Multi-phase plan](multi-phase-plan.md) exists, use its store, read its `plan.md` first, and take the units from its PR sections. Your tracker file lives in the store. It lists the goal, each worker with its unit, worktree, state (running, done, replaced, or absorbed), and PR link, each PR's last verdict with its head SHA, and the decisions waiting on the user. Each sub-coordinator keeps its own tracker file in the store, and yours points at each one, so no two agents write the same file ([`principle-separate-before-serializing-shared-state`](../../principle-separate-before-serializing-shared-state/SKILL.md)). Read and follow [`handoff`](../../handoff/SKILL.md) in decision-trail mode, with the trail in the store. Watch each PR with the runtime's PR and CI event subscriptions when it has them. Call no scripts yourself, run no polling loops, and never relay messages or status between agents.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners. The owner is a role, not one agent. Once an owner agent returns, a fresh agent with consolidated scope takes the role's next round, per [cortex's Subagents section](../SKILL.md#subagents). A stop or hold order to a running agent is not reuse.
- **The owner loads the real skills.** Spawn each owner as a fresh background subagent of the general kind. It is not a [`cortex-agent`](../../../../agents/cortex-agent.md) delegate, because a delegate never follows another workflow and stops when its task needs one. It never opens this file, so its kickoff gives the absolute paths of the two `SKILL.md` files it follows, resolved from the cortex skill directory's real path. The owner reads and follows [`babysit`](../../babysit/SKILL.md) to reach merge-ready, then reads and follows [`shipping`](../../shipping/SKILL.md) to land.
- **The kickoff is the babysit ask.** It assigns the babysit loop and its mode, `background` or `check`, never `drive`, because `drive` stops a subagent finishing its turn. Babysitting starts on the user's ask, and the kickoff is that ask. The owner is exempt from the rules in [Opening a PR](opening-a-pr.md) and [Babysit](babysit.md) that hold babysitting until a whole stack is built. Babysitting never rebases. Its Invariant 3 reports rebases to the PR's owner. An owner babysitting its own PR is that owner, as in [Autopilot full](autopilot-full.md). It rebases its own branch and pushes with `--force-with-lease` pinned to the SHA it last pushed or took over. On any push it did not make, it stops and reports to you.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including the report of each unit it depends on, pasted in full. Workers can't see their siblings. Run each worker in its own git worktree on its own branch, never in your checkout or a sibling's. A worker that drives a single local resource, such as a simulator or a dev server port, gets its own instance or waits its turn. Pick each worker's model by its role, per [cortex's Subagents section](../SKILL.md#subagents).
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Spawn it per cortex's Subagents section like any delegate. It never opens this file and runs no playbook. Its kickoff pastes this file's Topology and Supervision sections in full as the rules for its area, with the area's goal, its units, the program store's path, and the path of its own tracker file there. In those rules it is the coordinator, and you stand in for the user. Stop at three levels: you, sub-coordinators, and workers. When the runtime does not let a subagent spawn its own subagents, skip this layer and keep each area's workers under you. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Fork when new work needs a worker's built state,** such as its checkout, uncommitted changes, or a running process. When the runtime cannot fork an agent, resume that worker instead, per cortex's fresh-by-default rule. Message a worker only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** on a different model family than the author when the runtime offers one. The owner merges only on that verifier's pass at the current head. It merges only when the user's request covers landing, as in "own this migration until it lands". Otherwise it stops at merge-ready, and your reply lists the PR for the user to land. The Always-pause list in [`principles`](../../principles/SKILL.md#autonomy) still binds.
- **Each owner lands only its own PR.** The verifier's pass is the independent verdict that step 1 of [`shipping`](../../shipping/SKILL.md) asks for. The owner runs that skill on its own PR once that PR is the lowest unmerged one in its stack. It skips step 4's third item, the retarget and the patch move onto the merge result, because that work belongs to the owner of the PR above. After a parent merges, that owner does it on its own branch, on your word. No owner retargets or pushes another owner's PR.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge (merge-ready when the request does not cover landing) before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a check through the repo's `verify-*` skill, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned, and through each sub-coordinator's tracker every worker it spawned, as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, the decisions waiting on the user, and the paths of the program store, the tracker, and the decision trail.
