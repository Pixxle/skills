### Hillclimb

**You own the metric and the experiment's integrity. Supervise and review. Delegate the attempts.** Use this for sustained, iterative improvement of one measurable thing against a target. A one-off fix is [Bug fix](bug-fix.md) or [Perf issue](perf-issue.md). This is the loop.

The core discipline is one change, one measurement, keep or revert. Never stack untested changes. Never claim a win from code inspection ([`principle-prove-it-works`](../../principle-prove-it-works/SKILL.md)).

1. **Ground the workload and architecture before you choose the metric.** Read and follow [`how`](../../how/SKILL.md) over the target. Name the realistic workload dimensions that can move the result (data size, history, state, concurrency). Select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix one metric, the direction that counts as better, and a checkable stop predicate. The predicate pairs a target with a floor on attempts, so a lucky early win can't end the run. "At least 50% better than baseline and at least 10 iterations" has this shape. Use the user's numbers when given. Otherwise agree them with the user.
2. **Build the measurement harness, prove its sensitivity, then freeze it** ([`principle-build-the-lever`](../../principle-build-the-lever/SKILL.md)). Read [`principle-explain-the-number`](../../principle-explain-the-number/SKILL.md) before you measure. Run contrasting realistic workloads. Confirm the target case reproduces the symptom and the easier cases separate as expected. If the harness cannot tell them apart, revise the workload or the metric. Vet the harness by reading and following [`benchmark-checklist`](../../benchmark-checklist/SKILL.md) before you freeze it, and make it print its error count and a count of the work done. Once frozen, one repeatable command emits the metric, sampled enough to clear the noise (median of N, not a single run). Record the baseline metric and a green run of the regression gate (the tests that must keep passing) before any change.
3. **Open the decision log:** read and follow [`handoff`](../../handoff/SKILL.md) in Decision trail mode. For this loop the log is `decision.tsv`, one row per attempt. Its columns extend handoff's columns and keep `ts` and `phase` first: ts, phase, id, hypothesis, change, before, after, delta, tests, verdict (kept or reverted), note. Phase is `attempt` on every attempt row. A run boundary gets a `start` row exactly as handoff defines it. Its `note` names the `ts` range of the earlier rows and this run's id, and its attempt cells stay empty. Handoff still owns the row, start-row, and audit rules (single-line cells, append-only). Handoff's log helper writes only its six default columns, so append each row with `printf` and apply the helper's cleaning rules yourself. Strip tabs and newlines from every cell. Prefix a cell that starts with `=`, `+`, `-`, or `@` with a single quote, so a delta such as `-12%` is written `'-12%`. Read the log before each attempt. Keep it out of the tree (gitignored).
4. **Ground each hypothesis in the architecture model from step 1.** Each one names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses by the performance mantras in step 2 of the [Perf issue](perf-issue.md) playbook. Borrow only their order, not that step's stop rule.
5. **Loop, one hypothesis per iteration.**
   - Hand the change to a subagent with a tight scope, per [Subagents](../references/subagents.md). A mechanical attempt goes to a fast model. A cross-cutting or subtle one goes to the strongest judgment model. Supervise and review the diff rather than typing it ([`principle-guard-the-context-window`](../../principle-guard-the-context-window/SKILL.md)). When several independent hypotheses are live, fan them out to parallel subagents, each in its own worktree ([`principle-separate-before-serializing-shared-state`](../../principle-separate-before-serializing-shared-state/SKILL.md)).
   - Measure before and after with the frozen harness, and run the regression gate. Read the harness's error count and work-done count on both sides. A delta you cannot explain goes back through [`principle-explain-the-number`](../../principle-explain-the-number/SKILL.md) before you accept it.
   - Accept only when the metric moves past noise and the gate stays green. Otherwise revert the change in full. A tweak that "might help" is not kept.
   - Make one commit per accepted fix. Stage only the files you changed (`git add <files>`, never `-A`). Log the row either way, kept or reverted.

   Each iteration ends in a check before the next begins ([`principle-sequence-verifiable-units`](../../principle-sequence-verifiable-units/SKILL.md)). If the run is unattended, borrow only the wake mechanism from the [Autonomous run](autonomous-run.md) playbook, not its stop rule.
6. **Push past the first plateau.** On a stall, or several rejects in a row, pivot category, combine near-misses, re-read the source, or try something more radical before you conclude the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior. Keep a simplification that holds the number ([`principle-laziness-protocol`](../../principle-laziness-protocol/SKILL.md)).
7. **Stop when the predicate is met,** or when the remaining ideas are marginal and not worth their cost. Don't relax the predicate to meet it. Don't quit while cheap untried hypotheses remain. If you are stuck, surface it instead of spinning. Vet the baseline-to-final number by reading and following [`benchmark-checklist`](../../benchmark-checklist/SKILL.md) before you report it.
8. Run [Opening a PR](opening-a-pr.md) with the accepted commits stacked in the order they landed.

**Reply:** the metric and target, baseline to final with the percent delta (with run count, range, and limiter), iterations run (kept versus reverted), each accepted fix on one line, the `decision.tsv` path, and the best idea you would try next if pushed further.
