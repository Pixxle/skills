### Refactor

**You own the contract. The structure changes. The behavior does not.** Distinct from [Feature](feature.md), which adds behavior, and [Bug fix](bug-fix.md), which corrects it.

If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. The split-out change needs its own explicit acceptance and runs through [Feature](feature.md) or [Bug fix](bug-fix.md). A redesign is allowed, but name it and route to [Feature](feature.md). This playbook is the focused-to-medium change. Step 0 routes the rest.

0. **Route by scope.** Work that matches none of these routes continues at step 1.
   - Full-scale refactoring of the whole system (a system-wide, proposal-first discovery sweep across modules) → read and follow [`thermo-nuclear-refactor`](../../thermo-nuclear-refactor/SKILL.md), including its investigation brief. Its discovery and proposals stand in for steps 2 to 4. Hold each accepted proposal it implements to steps 1, 5, 6, and 7 (pin it before it moves, revert it if reader load does not drop), then run step 8.
   - A standing multi-day program (many stacked PRs, a fleet of subagents under one coordinator) → [Orchestrate](orchestrate.md), per rule 3 of cortex's [When rows overlap](../SKILL.md#when-rows-overlap). This holds even for a migration across many call sites.
   - Large or cross-cutting structural work short of a whole-system sweep (a migration across many call sites, an ambitious multi-part reshape) → read and follow [`figure-it-out`](../../figure-it-out/SKILL.md).
   - A maintainability-only review the user asked for → read and follow [`thermo-nuclear-code-quality-review`](../../thermo-nuclear-code-quality-review/SKILL.md), instead of this playbook or before step 1.
   - Focused-to-medium refactor with structural quality in scope → spawn [`thermo-nuclear-code-quality-review`](../../thermo-nuclear-code-quality-review/SKILL.md) in parallel with step 5's mechanical edit lane (or with [`swarm`](../../swarm/SKILL.md) when reviewing the reshape), then keep its blocking findings before Opening a PR.
1. **Pin the behavior contract first.** Read and follow [`how`](../../how/SKILL.md) over the affected subsystem to learn the contract. Then write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. If the area has no coverage, write the pin before touching structure. Type check and lint are not a pin.
2. **Name the structure the code is missing** per [`principle-model-the-domain`](../../principle-model-the-domain/SKILL.md). Boring code stays when the shape is already clear and local. The reshape must delete branches or invalid states, not add indirection.
3. **Name the target shape.** State what the module layout, types, and call graph should be if built today ([`principle-foundational-thinking`](../../principle-foundational-thinking/SKILL.md), [`principle-redesign-from-first-principles`](../../principle-redesign-from-first-principles/SKILL.md)). If the target crosses a function boundary, read and follow [`architect`](../../architect/SKILL.md) for parallel design exploration of the shape before the move.
4. **Subtract before you add.** Delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape ([`principle-subtract-before-you-add`](../../principle-subtract-before-you-add/SKILL.md)). The smallest change that reaches the target shape ships ([`principle-laziness-protocol`](../../principle-laziness-protocol/SKILL.md)). A speculative cleanup that "might help" gets reverted.
5. **Move in small behavior-preserving steps**, each keeping the pin green. For API reshapes, migrate every caller and delete the old API in the same wave ([`principle-migrate-callers-then-delete-legacy-apis`](../../principle-migrate-callers-then-delete-legacy-apis/SKILL.md)). No compatibility shims. No parallel old-and-new paths. Spot-check every rename against the actual files. Renames silently miss usages in strings, prose, and back-references. Delegate the mechanical edits to a subagent on a fast model, per [Subagents](../references/subagents.md), with a specific scope: the file paths, the names being moved, and the behavior to hold. A cross-cutting or subtle move goes to the strongest judgment model instead. Pick each subagent's reasoning effort for the job when the runtime offers a choice. Review every diff yourself.
6. **Prove behavior is unchanged** on the real artifact, not "it compiles" ([`principle-prove-it-works`](../../principle-prove-it-works/SKILL.md)). For larger reshapes, run an equivalence check: a script that diffs old and new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface through the repo's `verify-*` skill when it has one.
7. **Confirm the change is worth keeping.** The success measure is reduced reader load ([`principle-minimize-reader-load`](../../principle-minimize-reader-load/SKILL.md)). If the diff does not lower reader load somewhere, revert it.
8. **Rebase into small ordered commits.** A subtraction commit, then the reshape, then any follow-on cleanup. Shape them with [`principle-sequence-verifiable-units`](../../principle-sequence-verifiable-units/SKILL.md), so each behavior-preserving slice stays green before the next. Run [Opening a PR](opening-a-pr.md).

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior. On the whole-system route, add coverage and each proposal's verdict (accepted, rejected, deferred).
