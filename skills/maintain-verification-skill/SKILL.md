# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by [`create-verification-skill`](../create-verification-skill/SKILL.md), or any project-local verification skill with a feature map. The unit of rigor is the feature, not the sentence. Cover every feature file from source and exercise every feature live, without proving every bullet.

## Outcomes

Pick one and say which.

- `clean`. Every feature got source and live coverage, and nothing is worth shipping. No branch, no PR.
- `changed`. One PR ships proven doc, harness, or map corrections.
- `blocked`. Coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory (its `SKILL.md`, `features/`, and the harness scripts it owns) and the `.claude/skills` symlink that points at it. Never edit product code during a run. A behavior the map describes that the app no longer does is either doc drift or a product regression. Fix doc drift in the map. Report a product regression and do not paper over it in docs.

## Pass

0. **Locate the target.** Look for a project-local skill with Launch and Drive sections and a feature map, usually `.agents/skills/verify-*/` with a symlink at `.claude/skills/verify-*`. A symlink and its target are one candidate. Several real candidates means ask the user which one. None means stop and point the user at [`create-verification-skill`](../create-verification-skill/SKILL.md) instead of inventing a target. A missing or broken symlink is drift, so fix it.
1. **Index hygiene.** Read the feature map README and list its sibling files. Fix missing, extra, duplicate, or dead entries. Keep it light, with no generated inventory.
2. **Source wave.** Spawn one read-only subagent per feature file, in parallel. Each explains from source how the user-facing feature works, flags likely doc drift with citations, and returns one concise live-verification recipe. Subagents never drive the app and never edit files. Each returns a feature summary, its source entry points, likely drift or none, and one recipe.
3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift. Do not re-prove clean claims. Sweep recent churn (`git log` since the map last changed) for user-facing surfaces missing from the map. Require a concrete source path before calling one missing.
4. **Live pass.** Required even when source looks clean. You own all driving. Follow the verification skill's own launch model, either one long-lived instance driven serially (servers, UIs, a simulator or emulator) or a fresh isolated session per drive (short-lived CLIs). The skill's Launch section decides, not this one. Exercise every feature at least once. Hold three invariants the whole pass, whatever fails.
   - **Health before driving.** Never drive an instance you have not health-checked since it last did something surprising. Run doctor before the first drive, on each fresh session where sessions are the unit, and after any failed drive. Where doctor cannot see the failure (a wedged UI on a healthy process, a stuck system dialog on a simulator), reset to a known state or relaunch rather than hoping.
   - **Evidence survives.** Evidence captured so far survives every cleanup. Check it at its named location. Do not assume it.
   - **Nothing outlives its use.** Nothing a drive started outlives that drive's usefulness. Clean failed-iteration residue whether the session is stuck, exited, or shared. For a shared instance, clean the residue, not the instance.

   A doctor failure caused by skill drift is drift. Fix it under edit scope and retry once, restarting only what the fix invalidated, before calling the pass `blocked`. A feature that cannot be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, device, external state) and the route attempted. If the map omits that prerequisite, that is drift. Re-drive every harness fix from triage live before it ships. Final teardown happens after the last drive of the run, re-proofs included, so nothing outlives the run. Evidence stays, per the skill.
5. **Triage.** A wrong or missing user-POV description is doc drift. Fix it. Working behavior the harness cannot drive is a harness gap. Fix it under the generator's helpers rule (scripts executable, invocation shown in the skill body). App behavior that is actually broken is a product gap. Record it for the user with the failing drive and its evidence, keep it out of this PR, and offer a fix. On a yes, read and follow the [Bug fix](../cortex/playbooks/bug-fix.md) playbook with that drive as the repro.
6. **Ship or stop.** For `changed`, re-read every changed file, then open one PR of proven corrections by reading and following cortex's [Opening a PR](../cortex/playbooks/opening-a-pr.md) playbook. For `clean` or `blocked`, open no PR.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location. Do not commit them.

## Reply

Report the outcome, the features covered from source and live, each `verified-unreachable` feature with its prerequisite, confirmed drift and its fix, product gaps, and the PR link when `changed`.
