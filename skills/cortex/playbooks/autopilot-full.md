### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

1. **The operator's gates come first.** The operator's ask to autopilot the queue is the go. A request only to state the plan is not. The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program per **Forge** in [`playbooks/opening-a-pr.md`](opening-a-pr.md), and name it in every owner brief. Each owner is a subagent, in the cloud when the runtime offers it, that builds, opens its PR early per [`playbooks/opening-a-pr.md`](opening-a-pr.md), proves the change on the real artifact, babysits to green per [`playbooks/babysit.md`](babysit.md), and merges once steps 4 and 5 clear it.

   The code is ready only after the slop-strip and the [`no-comments`](../../no-comments/SKILL.md) pass, so the full swarm runs on finished code. Run the repo's checks for the touched paths on the committed head before the code-ready push and before any later push that needs a verifier. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and report merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI.

   Assume the VM dies. Soon after starting, push and start a decision trail in the root agent's store (path in the brief) per the decision-trail mode of [`handoff`](../../handoff/SKILL.md), then push each finished unit before you start the next. Each owner runs that mode's audit and cross-model review on its own trail before its final report, because each owner's run counts as its own outermost run for that rule. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that store, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify the code-ready head.** Fan out independent verifiers at the code-ready SHA per the [`swarm`](../../swarm/SKILL.md) skill. They re-run the gates, prove the load-bearing behavior live on the real surface through the repo's `verify-*` skill or a named driver, and audit the diff. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none. The verdict is not clean without the live lane, or before you audit the receipts in the owner's merge-ready report, meaning the evidence it cites for each claim, because no lane trusts a claim it has not checked.

   Block a PR only for a bug a user would hit, a failed gate, or a doc line the PR made wrong, and only with a failing run at the head or the wrong line. When an audit lane reports a user-facing bug without a failing run, read and follow [`interrogate`](../../interrogate/SKILL.md) with that finding as a lead, and block only if a run proves it. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** A verdict covers a patch and green CI covers one head, so the patch-id rule in step 3 of the [`shipping`](../../shipping/SKILL.md) skill can carry a lane's result to a new head, but every new head needs its own green CI. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed is the exception. Skip the rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land. If that install fails, the rebase must repair the lockfile. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
6. **Guard the gates and audit the run.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. Revert any change that disables a check or makes it soft-fail, because that check stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm an hourly self-paced loop to audit until no delegated work is left, because long runs drift and agents stall silently. Each tick re-reads this playbook and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent, down to the leaf lanes, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up on what changed and every item waiting on them, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
