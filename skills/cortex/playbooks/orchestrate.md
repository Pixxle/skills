### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** When the program has a [Multi-phase plan](multi-phase-plan.md), run it from that plan. Its unit list, stack order, and per-PR evidence feed each kickoff. Its full swarm per PR governs verification in place of the single verifier below, and execution starts only on the operator's go, as the plan's hand-back says. The program ends when the plan's **Close the program** boxes are checked. Without a plan, record the unit list, the stack order, and the predicate that ends the program before the first kickoff. At program close, run the end-of-run trail audit and cross-model review from the decision-trail mode of [`handoff`](../../handoff/SKILL.md) before the reply.

**Coordinate with your own tools.** Spawn workers as subagents. Keep a decision trail per [`handoff`](../../handoff/SKILL.md) in the agent store. Beside it, record each agent's id, unit, PR, head SHA, and verdict, so a resumed coordinator can pick the program up from the store alone. Wake on worker completion and on PR and CI event subscriptions when your harness has them. Without subscriptions, arm a self-paced heartbeat of an hour or more, so a stalled worker still reaches you. Write no orchestration script. Never forward a running agent's messages or status to another agent. A worker that needs another's result gets it in its kickoff.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. The exception is the retarget of its own PR to trunk after its parent merges, per step 4 of the [`shipping`](../../shipping/SKILL.md) skill. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff pastes in full each upstream report it depends on, because workers can't see their siblings. Run workers in the cloud when the runtime offers it, unless the work needs this machine, such as a runtime check through the repo's `verify-*` skill, local transcripts, a simulator, or auth that exists only here.
- **A sub-coordinator only when one area has many parallel workers.** It runs this playbook for its area and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Fork when new work needs a worker's built state,** such as its checkout, uncommitted changes, or a running process. Message an owner or sub-coordinator only for a fix round or follow-up on its own work. Never message a worker to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** on a different model family when the runtime offers one. The owner merges only on that verifier's pass at the current head, or on a pass that the patch-id rule in step 3 of the [`shipping`](../../shipping/SKILL.md) skill carries to it.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a check through the repo's `verify-*` skill, or an artifact. If you can't name the evidence, the unit isn't scoped yet. The kickoff also names the playbooks the worker follows, the paths it may and may not write, and the actions it must not take. An owner follows its build playbook, then [Opening a PR](opening-a-pr.md) and [Babysit](babysit.md). It merges its own PR with the merge command and read-back in step 4 of the [`shipping`](../../shipping/SKILL.md) skill, and after its parent merges, it retargets its own PR to trunk per that step.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict, and behavioral work needs more than a type check. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups in the decision trail.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Keep the mechanics from the user.** Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user. Ask only for what cortex's Always-pause list and fork rule reserve for the user, or for a dead end that survived a replan.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
