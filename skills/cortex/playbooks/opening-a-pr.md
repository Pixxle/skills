### Opening a PR

1. **Worktree.** Work from a git worktree off trunk. Subagents inherit it, and subagents on separate branches each get their own worktree. Two subagents on one branch take turns, and the next one runs `git fetch && git reset --hard origin/<branch>` only after the previous one pushed. When the branch holds unrelated work, save your change as a patch, open a fresh worktree, and apply the patch there. When a worktree is tangled, reset it from trunk and redo the change minimally.
2. **Commits.** Write every commit message, PR title, and PR body in plain technical English. Use one word for each action, keep the articles, and use a plain verb over an `-ing` form where one works. Commit often, then rebase into small ordered commits before you open the PR. Order them per [Sequence Work into Verifiable Units](../../principles/sequence-verifiable-units.md), so each commit lands on its own. Amend when a fix belongs in the last commit, and add a new commit when the fix is separable. A commit body does not restate the subject.
3. **Slop-strip.** Before each commit, remove defensive checks abnormal for that code, casts that dodge the type checker, dead compatibility paths, unrelated edits, and style that breaks from the file. Before you ask for review, read and follow [`no-comments`](../../no-comments/SKILL.md) on the diff. Real-surface proof and a verifiable commit sequence must hold before you declare code-ready or ask for review. Neither blocks the create call, so open the PR early when CI and bots should run alongside the work.
4. **Forge.** Resolve the forge before the first PR operation, and keep that choice for create, edit, view, watch, and merge. GitHub CLI (`gh`) is the default. Prefer `origin pr ...` when `command -v origin` succeeds and Origin can resolve the repository. Otherwise stay on `gh`, record the fallback, and do not require Graphite (`gt`). When the run provides a built-in PR tool, create, edit, retarget, and mark ready through it, because a CLI-made PR misses what the tool tracks. Use the forge for everything the tool does not cover.
5. **Titles.** Follow the repo's title convention when its history shows one. Otherwise use Conventional Commits, `type(scope): subject`, with no trailing period. The type is one such as `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. The scope is the area, such as `cortex`. The subject is short and imperative and names a real symbol when one carries the change, for example `fix(cortex): target the parent branch for stack children`.
6. **Description.** The body is a one-minute briefing for a reviewer who has the diff. It becomes the squash commit body, so keep it under about 40 lines. Use `##` headings, not bold lead-ins, in this order, and drop a section with nothing to say:
   - `## Why`: the user's goal, then the problem and approach, in 1 to 3 short sentences. No SHAs, rebase history, or "based on main" preamble.
   - `## What changed`: 1 to 3 short bullets. Name a real symbol or path only when it carries the change, and name both sides of a rename or retarget.
   - `## Scope`: always. 1 to 3 short items on what it covers and what it leaves out on purpose, such as a follow-up or a known gap. No symbols, paths, or file-by-file list.
   - `## Tradeoffs`: only rejected alternatives a reviewer would otherwise ask about.
   - `## Blast radius`: 1 to 2 sentences on who or what it touches and why that is safe or risky. If trunk is red, state the cost of leaving it red.
   - `## Verification`: 1 to 3 bullets, each a real run path and its outcome. For perf, give one primary number with its unit as `before → after`, and link the arena or swarm directory for the rest.

   After the sections, attach videos or screenshots when they prove a claim. Full SHAs, swarm or arena lane lists, method essays, metric tables, file-by-file checklists, and "CLEAN" verdicts go in a linked artifact, not the body. Then read and follow [`unslop`](../../unslop/SKILL.md) on the title, body, and commit messages.
7. **Size and stacks.** Prefer five narrow PRs to one large PR. Branch from trunk only for independent work. A stack is a chain of base branches. The root PR targets trunk, and each child branch rebases onto its parent's exact tip and targets the parent branch. Rebase the root on trunk before substantial stack work.
8. **Create ready.** Open every PR ready, never as a draft. Through a built-in PR tool, set `draft: false` on every create call, because the tool can default to draft. Without one, create with `origin pr create --status open --base <base>` or `gh pr create --base <base>`, and retarget with `origin pr edit <pr> --base <base>` or `gh pr edit <pr> --base <base>`. If a PR still opens as a draft, mark it ready through the tool, `origin pr ready <number>`, or `gh pr ready <number>`. Read the PR back with `origin pr view <number>` or `gh pr view <number>` before you state its status.
9. **Post the URL, then keep building.** Opening a PR does not start a babysit. Finish the phase or stack, and babysit only when the user asks after the stack exists, because a babysit per PR stalls the build and spends checks on commits that later waves restart. A subagent returns the URL to its parent without babysitting. The exception is an Autopilot-full, Autopilot-stack, or Orchestrate owner. Its brief assigns the babysit loop and is the ask [`playbooks/babysit.md`](babysit.md) waits for. The owner starts the loop after its code-ready report, and that timing overrides the rule here and in the [`babysit`](../../babysit/SKILL.md) skill that holds babysitting until a whole stack is built.

**Reply:** each PR URL with its base branch, in stack order.
